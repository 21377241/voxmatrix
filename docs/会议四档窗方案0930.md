# 会议四档窗方案（S / M / L / XL）

> 适用能力：Long-form ASR、Diarization、Speaker Attribution（三类共用同一批窗）。  
> 代码：`suites/native/windowed_ondevice.py`（构建）、`scripts/build_windowed_ondevice_indexes.py`（构建入口）、`scripts/sample_windowed_ondevice_eval.py`（Native 抽样）、`scripts/build_full_windowed_indexes.py`（同步 Full Index）。  
> 构建产物：`/mnt/afs/eval_data/windowed_ondevice/`。记录日期：2026-09-30。

## 1. 为什么分四档

- 三类能力的官方协议都是**整场会议**（数十分钟），Qwen3-Omni 无法稳定处理，只能切窗评测（adapted，不等于官方整会分）。
- 旧方案是 30s（diar / attribution）和 30–60s（long-form）两套独立窗，窗长单一、三类能力不同源，无法看出「窗越长模型越差」的趋势。
- 新方案用**同一起点、四个窗长**的嵌套窗：同一段会议内容在四档之间只差长度，可以直接比较窗长对分数的影响；三类能力的金标出自同一份时间轴，互相可对照。

## 2. 四档定义

| 档 | 允许窗长 | 典型时长 | 实际均值（四数据集） |
|---|---|---|---|
| S | 25–45s | ≈30s | 28–31s |
| M | 50–90s | ≈1min | 53–57s |
| L | 100–150s | ≈2min | 104–106s |
| XL | 240–330s | ≈5min | 244–250s |

窗长的具体取值由边界点决定（见 §3.3），所以落在范围内的哪个位置不固定；实际多数贴近范围下限。

## 3. 构建流程

### 3.1 数据来源与时间轴

每场会议先整理成一条时间轴：`(start, end, speaker, text)` 的句段列表。

| 数据集 | 使用的划分 | 会议数 | 标注来源 | 音频来源 |
|---|---|---:|---|---|
| AISHELL-4 | test | 20 | TextGrid（无文本层时退回 RTTM） | 远场 8 通道 flac，连续裁剪 |
| AliMeeting | Test_Ali_far + Eval_Ali_far | 28 | TextGrid（跳过「内容层 / 角色层」两层） | 每场第一个远场 `_MS*.wav`，连续裁剪 |
| AMI | test + dev（SDM） | 34 | SDM 逐句切片文件名里的起止时间 + ASR manifest 文本 | 逐句 SDM 切片按时间戳**叠加还原** |
| CHiME-6 | test + dev（ref array） | 4 | ref array 逐句切片文件名里的起止时间 + ASR manifest 文本 | 窗内多数句所属阵列 `U0x` 的 4 通道取均值 |

文本清洗：去掉尖括号标记（`<sil>`、`<%>`、`<noise>`、`<laughter>` 等），清洗后为空的句段在 TextGrid 解析阶段直接丢弃。

### 3.2 候选边界点

窗的起点和终点只能落在以下位置：

1. 会议开头（0s）和结尾（最后一句结束时间）；
2. 每个句段的开始和结束时间；
3. 相邻句段之间静音 ≥0.3s 时，静音的中点。

### 3.3 嵌套组（family）

对每个候选起点 `t0`：

1. 按 S → M → L → XL 顺序，在该档允许的窗长范围内找**最早**的一个边界点 `t1`，要求窗口 `[t0, t1]` **不切断任何句段**（与窗口相交的句段必须完整落在窗内，容差 0.05s）。
2. 每一档的 `t1` 必须比上一档更晚；某一档找不到合法 `t1` 就停止，更长的档也不再生成——这就是「缺档」的来源（常见原因是长句跨过范围上限，或接近会议结尾）。
3. 必须至少有 S 档，且 **S 窗内 ≥2 个说话人、语音占比 ≥0.3**，否则整组丢弃。

因为四档共用起点、终点递增，所以 **S ⊂ M ⊂ L ⊂ XL**。

### 3.4 每场会议选哪些组

- 每场会议最多 **6 组**，任意两组起点间隔 **≥150s**（长窗之间仍可能部分重叠，短窗基本不重叠）。
- 先把会议按时长三等分，前 / 中 / 后三段各取一组：优先档数最全的，同等条件取最早的。
- 再从剩余候选中按时间等步长补齐到 6 组。
- 最终按起点时间排序，编号为 `{数据集}_{会议}_f00…f05`。
- 选组是确定性的：参数里的 seed 目前未参与选组（预留给以后分层抽样）。

### 3.5 音频生成

- 先生成该组最长的一档（通常是 XL），短档直接取它的**前缀**（`ffmpeg -t`），保证四档音频开头完全一致。
- 统一输出 16kHz 单声道 wav；多通道源用 ffmpeg `-ac 1` 下混。
- AMI 叠加还原：把窗内每句 SDM 切片按时间戳放回时间轴相加，峰值超过 1 时整体归一；句间空隙为纯静音（没有真实会议室底噪）。
- CHiME-6：取窗内多数句所属的参考阵列，4 个通道取均值。
- 已抽查四数据集的 S / XL 音频：时长与索引记录一致，16kHz 单声道。

### 3.6 三种金标（同一窗、同一时间轴）

| 能力 | 金标 | 内容 |
|---|---|---|
| Long-form ASR | `text` 字符串 | 窗内全部句段按开始时间排序后拼接，**包含重叠插话** |
| Diarization | `{"segments": [{start, end, speaker}]}` | 窗内句段，时间换算为相对窗起点 |
| Speaker Attribution | `{"utterances": [{id, speaker, text, start, end}]}` | 同上，另带文本；清洗后文本为空的句段不进金标 |

Diarization / Speaker Attribution 额外要求窗内 ≥2 个说话人（S 已满足，长档是 S 的超集，所以实际不会因此少行）。

## 5. Native 评测集抽样

- 每个数据集取 **20 个完整组**（四档齐全，且三类能力都齐全）× 4 档 = **80 条**，三类能力用同一批组。
- 抽样：会议按 seed=42 打乱，组在会议内打乱，然后**轮流从每场会议取一组**，所以 AISHELL-4 / AliMeeting / AMI 各覆盖 20 场不同会议；CHiME-6 只有 23 个完整组、4 场会议，取其中 20 组。
- 行序按组排列（同组四档相邻），Catalog 槽设 `limit_step: 4`，任何 limit 都取整到完整组，保证四档条数一致。默认 `NATIVE_LIMIT=10` 会取整为 8 条（2 组，仅作 smoke）。
- 抽样记录：`/mnt/afs/eval_data/windowed_ondevice/summaries/eval_subset.json`。

## 6. Full Index

- 仓库路径：`mesh_eval/data/full/{long_form_asr,diarization,speaker_attribution}/`，文件名与 Native 相同。
- 保留全部可用行（含缺档组）；行序按会议、起点排序，组内 S/M/L/XL。
- 条数：AISHELL-4 480 / AliMeeting 655 / AMI 792 / CHiME-6 93（三类相同）。Native 80 条与 Full 对应行逐字一致。
- 旧 30–60s 索引及音频移到 `mesh_eval/data/full/long_form_asr/legacy_30_60/`。

## 7. 评测与计分

- 一个（能力, 数据集）是一个 Catalog 槽，共 3 × 4 = **12 槽**，已计入主分。
- 每个槽按 `window_bucket` 分组，同时报 S / M / L / XL 四档分和槽总分；四档不另设权重，槽总分按该指标的常规聚合方式对全部样本计算。

| 能力 | 主指标 | 聚合 |
|---|---|---|
| Long-form ASR | 中文 CER / 英文 WER | corpus-level（总编辑距离 / 总参考字词数），`wer-zh-windowed` / `wer-windowed` |
| Diarization | DER | `mesh`：按参考语音时长加权（总错误时长 / 总参考时长） |
| Speaker Attribution | cpCER%（最优说话人置换后的 CER / WER） | `mesh`：逐条 cpCER 取均值 |

## 8. 与官方协议的差异和已知局限

- **不是整会评测**：窗口分数不能当作 AISHELL-4 / AliMeeting / AMI / CHiME-6 官方整会 CER / DER / cpCER。
- **用了 dev 划分**：AMI、CHiME-6 合用 test + dev，AliMeeting 合用 Test + Eval，以获得足够会议数；与只报 test 的官方结果不同。
- **AMI 音频是还原的**：逐句切片叠加，句间是静音，比真实 SDM 连续录音更干净。
- **CHiME-6 规模小**：只有 4 场会议，20 组中多组来自同一场会议，分数方差大。
- **金标包含重叠插话**：Long-form ASR 的参考文本把重叠句也拼进去，模型漏听插话会计为删除错误。
- **中文数字读法**：金标有时写汉字读法（如「零零六」），hyp 的阿拉伯数字经归一后不一致，会抬高 CER；与其他中文 ASR 槽同口径，不做特判。
- **未覆盖**：MISP、SBCSAE 的 long-form，MISP diarization，AISHELL-5 / CN-Celeb attribution 均为 blocked（不在四档构建范围内）。
- **相邻组可能重叠**：组起点间隔 150s，小于 XL 窗长，同一会议的两个 XL 窗可能有部分内容重复。

## 9. 复现

```bash
# 1. 构建全量四档窗（写 /mnt/afs/eval_data/windowed_ondevice/）
python scripts/build_windowed_ondevice_indexes.py            # 默认 family-gap 150、每会议最多 6 组

# 2. 抽 Native 评测集（每数据集 20 组 × 4 档）
python scripts/sample_windowed_ondevice_eval.py --per-bucket 20 --seed 42

# 3. 同步 Full Index 到仓库
python scripts/build_full_windowed_indexes.py

# 4. 重新生成 Catalog，并提交正式评测（每槽 80 条）
python suites/native/_build_coverage.py      # 由 Catalog 生成运行配置
bash scripts/submit_native_windowed_ondevice.sh
```
