## Native 配置管理原则

当前 Native 评测以以下文件作为主配置事实来源：

```text
suites/native/catalog.yaml
```

后续 Native 的 capability、Benchmark、Dataset、Prompt、Evaluator、Aggregator 和执行状态，优先在 Catalog 中维护；其他配置和索引按 Catalog 同步：

- `mesh_eval/registry/dataset/`：同步 Dataset 注册；
- `registry/prompt/`、`mesh_eval/registry/prompt/`：同步 Prompt；
- `registry/evaluator/`、`mesh_eval/registry/evaluator/`：同步 Evaluator；
- `registry/agg/`：同步 Aggregator；
- `mesh_eval/data/native/`：同步具体样本索引；
- `annotation/benchmark_subset_manifest.jsonl`：保留作为数据来源、协议和统计溯源；
- `mesh_eval/config/capability_protocols.v2.yaml`：保留作为通用协议和校验参考。

如果其他配置与 Native Catalog 不一致，以 Catalog 的 Native 执行口径为准，并应通过覆盖审计发现并修正。

## 1. Long-form ASR 是否保留

### 现状

- 当前使用 30–60 秒窗口，覆盖 AISHELL-4、AliMeeting、AMI、CHiME-6、MISP、SBCSAE。
- Native smoke 可正常生成窗口、读取音频并完成评测。
- Full Index 正在建立。

### 存在的问题

- 与句级 ASR 的能力边界还需要进一步明确。
- 会议数据存在重叠 speech，当前采用 `primary_pack_only`，尚未确认是否完全符合各 Benchmark 官方口径。
- 当前窗口和 reference 主要是工程化方案，尚未完成 Full Index 级别验证。

### 可能的解决方案

- 暂时保留 Long-form ASR 作为独立能力。
- 保持 `primary_pack_only` 主榜口径，同时记录被排除的重叠 segment。
- 按 Benchmark 核对官方协议，必要时增加 `all_overlapping_segments` 诊断口径。
- Full Index 完成后重新抽取 Native smoke 并复测。

### 讨论用样例

**同一次会议被切成「长窗 ASR」vs「30s diar」**（AISHELL-4 `L_R003S01C02`）：

| 能力 | sample | 窗 | gold 形态 |
|---|---|---|---|
| Long-form ASR | `aishell_4_lf_0000` | 4.835–38.842s（≈34s） | 拼接转写文本：`零零六 … 今天啊把各位都叫过来啊…` |
| Diarization | `aishell4_diar_…_w0000` | 0–30s | `segments[{start,end,speaker}]`，同窗 6 说话人 |
| Speaker Attribution | `aishell4_attr_…_w0000` | 0–30s | `utterances[{speaker,text}]`（同窗带字） |

**重叠 speech（同一 30s 窗内）**：`003-F` 13.376–14.306 与 `005-M` 13.23–14.495 时间重叠。Long-form 若用 `primary_pack_only`，插话侧可能不进 reference——讨论点是：官方会议 ASR 要不要把重叠段都拼进 ref。

## 2. Audio Caption 指标是否引入 FENSE

### 现状

- 当前使用 COCO-style 指标：CIDEr、SPICE、BLEU、METEOR、ROUGE-L、SPIDEr。
- AudioCaps 是一音频一条 reference；Clotho 是一音频五条 reference。
- FENSE 已完成框架接入和小样本后处理测试。

| 指标 | 主要衡量内容 |
|---|---|
| BLEU / ROUGE-L | 词面和句序重合 |
| METEOR | 词、词干、同义表达匹配 |
| CIDEr | TF-IDF 加权的 caption 相似度 |
| SPICE | 对象、属性、关系等场景语义 |
| SPIDEr | CIDEr 与 SPICE 的组合 |
| FENSE | SBERT 语义相似度 + 流畅性惩罚 |

### 存在的问题

- COCO 指标偏重词面匹配，对语义等价表达不够敏感。
- FENSE 只比较 prediction/reference 文本，不直接判断 prediction 是否符合音频。
- 目前缺少更大样本和人工评分，无法证明 FENSE 一定优于 CIDEr/SPICE。

### 可能的解决方案

- 保留 COCO-style 指标作为标准主指标。
- 将 FENSE 作为语义相似度和流畅性补充指标。
- 不把 FENSE 与 COCO 指标简单加权成单一总分。
- 通过 Full Index 和人工抽样，比较 FENSE、CIDEr/SPICE 与真实音频质量的相关性。

### 讨论用样例

AudioCaps Native smoke（n=10）后处理 FENSE 均值 ≈ **0.55**（`outputs/full_audio_caption_smoke/fense-posthoc.json`），同批 COCO：CIDEr≈0.37 / SPICE≈0.10。

| FENSE | pred（模型） | ref |
|---|---|---|
| **0.13**（低） | *A sewing machine runs while people talk in the background.* | *Constant rattling noise and sharp vibrations* |
| **0.85**（高） | *A large engine idles and then revs up, followed by a series of loud horn blasts.* | *An engine rumbles loudly, then an air horn honk three times* |

低分例：词面几乎无交集，语义也偏（缝纫机 vs  rattling）——FENSE 与人耳都低。高分例：引擎+喇叭，表述不同但语义近——FENSE 高、CIDEr 仍可能中等。讨论时强调：**FENSE 也不听音频**，只比 pred/ref 文本。

## 3. Semantic LLM Judge（Thinking）截断导致 parse_failed

### 现状

- Speech Translation / Code Switch 的辅轨已接入本地 `qwen3-omni-thinking` multimodal Judge。
- 流程：ASR 预填缓存 → 清显存 → 多卡分片 Judge（`max_new_tokens` 当前为 **512**，为提速从 2048 下调）。
- 最近一轮 smoke 结果：
  - Translation：30 条中 **11** 条 `judge_parse_failed`（有效 19；`score_0_100` 均值约 72.6）。
  - Code Switch：30 条中 **2** 条 `judge_parse_failed`（有效 28；均值约 90.7）。

### 存在的问题

- 失败样本的 `raw_judge_output` 停在 `<think>` CoT 中途，**没有 `</think>`，也没有最终 1–5 分**，解析器无法取分 → `skip_reason=judge_parse_failed`。
- 根因是 Thinking 生成长度触顶被截断，不是任务挂起或 ASR 缺失；translation rubric 推理更长，失败率明显高于 CS。
- 单纯加大 tokens 能减少截断，但仍可能因冗长 CoT / 评判标准偏差产生噪声（参见既有 A1B 经验）。

### 可能的解决方案

- **已做（2026-09-25）**：加强 Judge prompt 短输出约束（末行必须出 1–5 / Yes|No）+ Thinking `max_new_tokens=2048`；听→文 Judge 改推理后端。
- **已做（2026-09-26）**：评测 + Judge + speech 默认统一 `vllm_omni`（`Qwen3OmniVLLMOmni`）。QA 重测入口：`scripts/submit_native_qa_vllm_retest.sh`。
- 若仍有 parse_failed：仅对失败条再加大 tokens，或对 translation 改 Instruct 辅轨。
- 主榜仍以词面/协议指标为准；Judge 分数继续作为辅轨，parse_failed 单独报告，不与主指标加权。

### 讨论用样例

来源：`outputs/native_translation_smoke/translation-local-llm-judge.jsonl`（30 条中 11 条失败）。

**失败条** `CoVoST_2_zh_en_bidirectional_a7fce634e6df`  
- pred：`我的功能是什么?`　ref：`我的职责是什么？`  
- `raw_judge_output` 长约 2044 字，**无 `</think>`、无最终分数**，停在 adequacy 推理中途：

```text
<think>
Got it, let's evaluate this. The source is "What is my function?" and the
response is "我的功能是什么?" while the reference is "我的职责是什么？".
First, check adequacy. The source asks about "function", which in Chinese
can be translated as 功能 ... or 职责 ...
...
The scoring criteria: primary is adequacy—preserve meaning, entities,
numbers, negation, intent. The intent here is to ask about the user's
role/function.
← 此处截断，没有 </think> 与 "5"
```

**对照成功条**（同文件）：CoT 后正常收尾 → `</think>` + 单独一行 `5` → `score_0_100=100`。

说明给讨论：不是「Judge 判错」，而是 **Thinking 512 token 写完 CoT 就没额度打分**；translation 比 code-switch 更容易踩中（失败 11 vs 2）。

## 4. 会议类能力（Diarization / Speaker Attribution）是否坚持 30s 窗（vs 整会官方口径）

### 现状

- **正式协议**都是整段会议：
  - diarization：整会 → `segments[{start,end,speaker}]` → **DER**
  - speaker_attribution：整会 → `utterances[{speaker,text}]` → **cpCER%**
- Native / smoke 因 Qwen3-Omni 无法稳定处理数十分钟长会，**两类任务统一切 30s 多说话人窗**（adapted；常复用同一批 clips）。
- Diarization：Catalog 四槽 `diagnostic`，misp `blocked`；prompt-v2 + normalize 已落地；Full Index 未建。
- Speaker Attribution：Catalog 四槽 `diagnostic`，cn_celeb `blocked`（SID 错挂）；已有可评 cpCER；Full Index / CHiME-6 未建或未挂。

### 存在的问题

- **与官方整会口径不一致**：窗边界与抽样影响 DER / cpCER%，不能直接当整会榜。
- 与 Long-form ASR 的 30–60s 窗策略相关，但三类能力是否共用窗、如何标注尚未统一论证。
- 短窗是 Omni 工程缓解，不是协议本身要求；正式整会需长上下文后端或「分段再聚合」的评测定义（未定）。

### 可能的解决方案

- **短期**：diar / attribution 共用 **30s adapted** diagnostic 口径，报告与 Catalog note 写明非整会。
- **中期**：按同一 30s 约定建 Full Index；可选 60s / 变长窗消融。
- **长期**：若对齐官方整会协议，再定整会或官方 segmentation + 可长上下文后端；Omni 短窗分数不与专用 diar/ASV SOTA 横比。

### 讨论用样例

同一 AISHELL-4 会话 `L_R003S01C02` 前 30s（`aishell4_diar_…_w0000`）：

- **官方 diar 形态**：整会 RTTM → DER；我们只给窗内 9 段，例如：

```text
006-M  4.835–6.445
002-F  6.927–8.807
004-M  8.847–9.802
003-F 10.188–11.073
005-M 13.230–14.495   ⎫ 重叠
003-F 13.376–14.306   ⎭
…
```

- **官方 attribution 形态**：整会 → 带说话人的转写列表；同窗 `aishell4_attr_…` gold 是 `utterances`：`006-M:"零零六"`, `002-F:"零幺三"`, …（点名轮次），评 **cpCER%**。
- **工程事实**：源 wav 可数十分钟；Native 只喂 30s clip。讨论话术：分数证明「短窗多说话人链路」，**不能**说「达到 AISHELL-4 官方整会 DER/cpCER」。

## 5. Target Speaker：自建数据 + Omni 门控局限（暂 diagnostic）

### 现状

- **任务**：双音频（enroll + command）→ `{"should_execute": true|false}`；Catalog `diagnostic`。
- **指标**（已拆两类错误，不再把 pred≠ref 全算进 `mis_execution`）：
  - **target_speaker_acc**：对不对
  - **mis_execution**：仅 false→true（不该开却开）
  - **missed_execution**：仅 true→false（该开却拒）
- clean Native smoke（10 条）：acc=**0.40**；按新口径离线重打约为 mis_execution=**0.10**、missed_execution=**0.50**（正例 5/5 全拒，负例 1/5 误开）。盘上 overall 仍可能是旧口径 `mis_execution=0.60`（未重跑前勿直接引用）。
- 审计 Job 15277 曾表现为负例易误开；与本轮「正例易拒」方向相反，说明门控偏置不稳定。

#### 数据来源（AISHELL-5 自建 adapted，非官方协议）

AISHELL-5 **没有**现成的 enrollment / command / `should_execute` 标注；官方是车载多说话人语料。当前 Native 10 对来自旧 `VoxMatrix/smoke_ts_all/` 迁入 clean：

- 索引：`mesh_eval/data/native/target_speaker_aishell_5.jsonl`
- 音频：`mesh_eval/data/native/eval_clips/target_speaker/aishell_5/`（20 个短 wav）
- 构建脚本已不在盘上；规则由 manifest + clip **反推备查**：
  1. 语料：AISHELL-5 `eval1`，按说话人 ID 取单说话人片段。
  2. 切段：自切短 utt（约 0.5–6 s），`ts_{pos|neg}_{i}_{enroll|cmd}.wav`；非整段会话门控。
  3. 说话人池 6 人：`P0127, P0128, P0174, P0173, P0187, P0188`。
  4. 正例 5 对：同人两段不同短音 → enroll / command。
  5. 负例 5 对：相邻说话人错配链；部分 clip 与正例复用。
  6. Catalog note 标明 adapted。

### 存在的问题

- **能力**：Omni 对「是否同一说话人 → 是否执行」不可靠（acc≈0.4），与 SV 同类短板；偏置可在「乱执行 / 拒执行」间翻转，只报一种错误率会误导；不宜作端侧安全/排行主分。
- **数据**：非官方协议，分数只能证明自建短片门控链路；n=10、短 enroll、clip 复用未论证；构建脚本缺失，正式榜需重新协议化。

### 可能的解决方案

- **短期**：维持 adapted diagnostic；acc 与 mis_execution / missed_execution **同时**报；文档写明自建数据 + 模型能力极限，不因分数改协议。
- **中期**：补可复现构建脚本（固定 seed、加长 enroll、禁复用）；更大样本看偏置是否稳定。
- **长期 / 正式安全评**：勿依赖 Omni 裸判；专用说话人门控 / ASV 管线；若要主榜，先冻结正式协议（注册时长、指令类型、噪声条件、金标来源）再扩 Full Index。

### 讨论用样例

产物：`suites/native/output/main/native-target-speaker--aishell-5.jsonl`（10 条 eval）。

| sample | enroll→cmd | should_execute | pred | 错误类型（新口径） |
|---|---|---|---|---|
| `aishell5_ts_pos_00` | P0127→P0127 | true | `{"should_execute": false}` | **missed_execution**（该开却拒） |
| `aishell5_ts_pos_01`…`04` | 同人 | true | 全 false | 正例 **5/5 全拒** |
| `aishell5_ts_neg_00` | P0127→P0128 | false | false | 正确拒识 |
| `aishell5_ts_neg_03` | P0173→P0187 | false | **true** | **mis_execution**（不该开却开） |

讨论话术：模型几乎「默认不执行」→ acc=0.4 主要来自正例全拒；若只报旧口径 `mis_execution`（把所有错都合进去）会说成「乱执行」，与真实偏置相反。enroll/cmd 仅约 0.5–6s 短片，也不是车载长注册协议。

## 6. Audio Reasoning 开放作答与分轨

### 现状

- **2026-09-26 起挂起不评**：Catalog 五槽 `status=blocked` / `suite=none`（mmsu / uro_bench / vocalbench / vocalbench_zh / voicebench）。
- 挂起前：五槽为 open QA（MMSU/URO 剥选项）；词面分轨长答 ROUGE-L、短答 exist-match；辅轨 LLM-Judge。
- URO MuChoEval 源自 MuChoMusic：选项含故意设计的 IR / CU / IU 干扰项（CU=听对但答非所问，IU=既不贴题也不贴音频），观感像「题干与选项错位」，**不是脏数据**；金标文本均在 A–D 内。Native AR 不沿用其 MCQ 协议，剥选项后只评短标签 gold。
- VoiceBench BBH 必须保留 Options 才能作答；exist-match 对长 CoT 易虚高，语义以 Judge 为准。

### 存在的问题

- 模型常输出长推理链，「只输出答案」约束偏软，词面轨不稳定。
- VocalBench-zh 单字谜底：模型推错字时 exist-match 与 Judge 都会低，属能力/题型本身难。

### 可能的解决方案

- 维持分轨：词面 + Judge 独立报告，不合成总分。
- 若需压 CoT：收紧 Prompt 或后处理抽取最终答案再算 exist-match（诊断用）。

### 讨论用样例

**1）「只输出答案」仍写长推理（VoiceBench BBH）**  
Prompt 末尾已写：`when you provide the final answer, please use the prefix "The answer is:" … provide the answer directly.`  
`bbh_hyperbaton_107`：ref=`(A)`，pred 长达 **~3700** 字，从形容词语序规则推到中途还在比对 Option (A)…——exist-match 若对整段做 contain，易因文中出现 `(A)` **虚高**；语义应以 Judge 为准。

**2）短答单字谜（VocalBench-zh）**——能力/题型本身难：

| sample | pred | ref | match |
|---|---|---|---|
| reasoning-000 | 乏 | 顺 | 0 |
| reasoning-007 | 佣 | 拥 | 0（形近） |
| reasoning-004 | 金 | 金 | 1 |

exist-match 与 Judge 都会低时，不宜解读成「分轨打架」，而是题难/听错字。

**3）URO / MuChoMusic 干扰项 vs BBH**  
MuChoMusic 每题 4 选项 = 正解 + IR（贴题但听错）+ CU（听对但答非所问）+ IU（双不相关）；URO MuChoEval 继承该设计（如问乐器却出现 tempo / 氛围类 CU）。Native 剥选项 → open 短标签（pred=`A. Guitar` / ref=`Guitar` 仍可 exist 命中）。BBH 选项与题干一体，必须保留。讨论「开放作答」时区分：有的槽必须留 Options（BBH），有的刻意剥掉（URO/MMSU）。

### 讨论用样例（两套 IF 为何不能合成）

**VoiceBench（文本约束 / 规则 checker）** `voicebench_ifeval_1001`：

```text
prompt: …write an itinerary… Shakespearean style. You are not allowed to use any commas…
instruction_id_list: ["punctuation:no_comma"]
→ mesh-ifeval 扫输出有无逗号 → constraint_satisfaction ∈ {0,1}
```

模型曾输出无逗号的莎翁风行程（`Hark! Attend good traveler…`）→ strict=1。这是 **文本格式约束**，不是听生成音。

**VocalBench（语音生成 + 官方 FR）** 同库题面举例：

| index | Sub-category | 题面要点 | 完整 FR 还要过 |
|---|---|---|---|
| 0 | Plain repeat | Repeat… without explanation + 复述长句 | 语义 Correct + **WER&lt;0.2** |
| 50 | With emotion | …with **angry** emotion + Text_emo=angry | + emotion2vec P(angry)&gt;0.5 |
| 100 | With speed | …at **half my speaking speed** | + 生成时长 ∈ (1.5,2.5)×缩放 query 时长 |
| 200 | Num | give me **five** suggestions | 仅语义 Correct |

讨论话术：一边是「禁止逗号」这种 IFEval，一边是「用愤怒语气半速复述」——轴不同，**禁止加权成一个 IF 总分**。

## 8. Spoken SLU（FSC / SLURP intent+slots）：**已定独立能力**，与 IF / tool_call 分列

### 定案（2026-09-26）

- 新建 Catalog 能力 **`spoken_slu`**，挂 FSC / SLURP 的 **intent+slots** 主轨。
- **不是 IF**：与 VoiceBench `constraint_satisfaction`、VocalBench 语音 FR 不同轴。
- **不是 tool_call**：tool_call 评 `{"tool","arguments"}`；SLU 评数据集固定 ontology 的 `{"intent","slots"}`。
- IF 侧原 `instruction_following__fluent_speech_commands` / `__slurp` 保持 **blocked**（注明已迁到 `spoken_slu`）。
- `tool_call__fluent_speech_commands` / `__slurp` 仍属 **tool_call**（ontology→工具投影）；与 SLU **分报**，当前随 tool_call 一并挂起不评。

### Catalog

| 槽 | status | 协议 | 主指标 |
|---|---|---|---|
| `spoken_slu__fluent_speech_commands` | diagnostic | `mesh-intent-slots` → `{"intent","slots"}` | **intent_acc**（辅 slot_f1） |
| `spoken_slu__slurp` | diagnostic | 同上 | 同上 |

Dataset：复用 `t4-fsc-instruction-following` / `t4-slurp-instruction-following`（adapter 未改名，能力归属已改）。

### 三种任务形态对照（同一口令）

| 维度 | **spoken_slu** | **tool_call** | **IF（VoiceBench）** |
|---|---|---|---|
| 输出契约 | `{"intent","slots"}` | `{"tool","arguments"}` | 自由文本 + instruction_id |
| Prompt | 枚举允许 intent + slot 名 | 注入 tool schema | “Follow every explicit instruction…” |
| 主指标 | intent_acc / slot_f1 | tool_acc | constraint_satisfaction |

```text
# spoken_slu ref
{"intent": "activate_lights", "slots": {"action": "activate", "object": "lights", "location": "none"}}

# tool_call ref（投影，另一能力）
{"tool": "control_device", "arguments": {"action": "activate", "object": "lights", "location": "none"}}
```

**易被误读成「不会遵循指令」的失败**（实为 ontology / 闭集外）：

| sample | pred intent | gold intent | 说明 |
|---|---|---|---|
| `fsc_2_…` | `change language_English` | `change language_none` | 近义但标签必须 exact |
| `fsc_4_…` | `resume` | （不在允许列表） | 模型自造 intent → intent_acc=0 |

结论句：**听口令填固定 ontology ≠ 文本约束 IF ≠ 选工具**；混在 IF 或 tool_call 里都会把 ontology 误差讲成别的能力差。
